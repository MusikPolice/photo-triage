# Development reference

How things currently are: the repository's layout, every recipe and dev switch, the Compose stack's details, logging's mechanics, the tests at each layer, and the setup history. Every feature PR that adds a recipe, a test, a hook property, a switch or a folder updates this file. It isn't a sensitive path (dev-environment §9), so changing it doesn't send a PR to the user for review.

The decisions behind it (where tools come from and what's pinned, the test strategy, the safety invariants, CI's design, and how work is tracked and merged) are in [dev-environment.md](dev-environment.md), whose changes the user reviews. A citation of "§N" here means this file. "dev-environment §N" means that one.

## 2. Running each piece

| Command | What it runs |
|---|---|
| `just dev` | `scripts/dev.sh`: runs the migrate step (`python -m photo_triage.db migrate`, as `just db-migrate`), then the API (`--reload`), the worker, the Vite dev server and Ollama, in one terminal, each line prefixed `api`, `worker`, `web` or `ollama`. The first three run natively in WSL. Ollama runs in Docker from `compose.dev.yaml`: the production stack's service and pinned image (`docker/ollama.yaml`) on `localhost:11434`, with its models in the `photo-triage-dev_ollama` volume. Its first start downloads the image, several GB. Before starting anything, `just dev` checks that Docker answers, and if it doesn't, it exits saying why (no `docker` command, not in the `docker` group, or Docker Desktop not running) and what to do. `just dev --no-ollama` leaves Ollama out, and skips that check; the scratch stack does this. Open the URL Vite prints (`http://localhost:5173`, which Windows browsers reach through WSL's localhost forwarding). The worker runs under `watchfiles`, which restarts it after its current job when backend code changes. Ctrl-C stops them all, the worker after its current job and Ollama's container through Compose, and if one exits the others are stopped. Extra arguments go to Vite, e.g. `just dev --host` to try it from a phone. Uses `.env` → `PHOTO_DIR=/mnt/sample-pictures` (read-only), local `data/` and `trash/` dirs. The API and worker each log a warning at startup that `TRASH_DIR` is on a different filesystem from `PHOTO_DIR`: expected in dev, where the sample library is read-only: trashing an item there is refused, and the API reports it as skipped, saying the two are on different filesystems (plan §6.8). To try the trash, point `PHOTO_DIR` at a writable copy and unset `TRASH_DIR`. To watch the Activity page at work, set `WORKER_NOOP_STAGE=true` in `.env` and run `just worker noop 500` in a second terminal. The migrate step backs the database up before applying a new migration, so after testing a branch that adds one, its revision stays in the dev database: back on a branch without it, `just dev` stops and says to downgrade from that branch, restore the backup from `DATA_DIR/backups`, or delete `photo-triage.db` in `DATA_DIR`. |
| `just api` | The API alone: `python -m photo_triage.api --reload`, on `APP_PORT`, from the repo root so `.env` and `./data` resolve there. Exits with a list of what's wrong if `PHOTO_DIR` is missing, or `TRASH_DIR` is `PHOTO_DIR` or contains it. `TRASH_DIR` defaults to `PHOTO_DIR/.photo-triage-trash`. Exits 1 without serving if the database isn't at the head revision, saying to run `just db-migrate`, or that the database is newer than the code: the API never migrates. API docs at `/api/docs`. `curl -N localhost:$APP_PORT/api/events` shows the Activity event stream. While any stream is open, the API reads the activity once a second on a connection of its own, and recounts jobs only after another connection has committed (`PRAGMA data_version`); the worker's state is read every time, so a stale heartbeat or quiet hours show within a second. On a stop or reload, the API ends open event streams so it doesn't wait for them, and browsers reconnect. |
| `just web` | The Vite dev server for `frontend/`, with hot reload. It proxies `/api` to the API on `APP_PORT`, which it reads like the backend does: the environment first, then the repo-root `.env`, then 8000. Run `just api` alongside. Extra arguments go to Vite, e.g. `just web --host` to reach it from another device. |
| `just web-sync` / `just web-fmt` / `just web-check` | Install the frontend dependencies as locked; format and auto-fix lint; run svelte-check, eslint, prettier, Vitest and `vite build` (part of `just check`). |
| `just api-types` / `just contract` | Regenerate `frontend/src/lib/api-types.ts` from the API's OpenAPI schema (`scripts/api_types.sh`: `python -m photo_triage.api.openapi`, then `openapi-typescript` and prettier); fail if the committed file is out of date (part of `just check`, and the CI `contract` job). Run `just api-types` after changing an API model or route, and commit the result. The frontend takes its API types from that file (`src/lib/api.ts`). |
| `just worker` | The worker alone: `python -m photo_triage.worker`, from the repo root like `just api`. At startup it exits 1 if the database isn't at the head revision, as `just api` does, without claiming a job. Only one worker runs per `DATA_DIR`: it holds an `flock` on `DATA_DIR/worker.lock` while it runs, and a second one (`just worker` alongside `just dev` or the stack) exits 1 saying a worker is already running, before it touches the queue or `worker.log`. The kernel drops the lock when the process dies, even by SIGKILL, so a crash leaves no stale lock; the file itself stays. `noop`, `pause` and `resume` don't take it. Then it counts any job left `running` when it last stopped as a failed attempt: the job goes back to its place in the queue, or is parked after 5 attempts. Then it reconciles the item stages (plan §6.11): it queues each registered item stage (`item_stages` in `photo_triage/worker/stages.py`; `scan`, `metadata_read`, `frames`, `thumbnail` and `clip` so far) for every active item it's due for, and logs `Reconciled stages, queued …` or `… nothing due`. It does this again after each walk. When an item stage's job finishes, the worker queues the stages after it that are now due for that item, by the same rule, in the transaction that marks the job done, so a new item flows through every stage without waiting for a reconcile. A run that reports its output unchanged queues nothing that's already done. Then it runs jobs in priority order until SIGINT or SIGTERM, finishing the job in progress first (a second signal stops at once). `just worker --once` runs every ready job and exits; jobs waiting out a retry backoff are left for later. The `metadata_write`, `walk`, `scan`, `metadata_read`, `frames`, `thumbnail` and `clip` stages run (plan §6.1–§6.3, §6.10); stages without a runner yet stay in the queue. A `metadata_write` job makes every write queued for its item (`metadata_writes`) in one exiftool call, recording each one's before and after values. With `EXIF_WRITES_ENABLED` unset, as in dev, where the sample library is read-only, it logs them as `dry_run` and leaves the file alone. After each layout fit, and at a reconcile if no grouping has followed the latest fit, the worker queues the `duplicates` batch job (`photo_triage.worker.duplicate_schedule`), which groups items whose embeddings are at least `DUPLICATE_SIMILARITY_THRESHOLD` alike into `duplicate_groups`, ranking each group's members for a keeper. Grouping again keeps each group's id and decision while its members stay the same (`photo_triage.pipeline.duplicates`). Every scan queues a `metadata_read` for its item, which reads its dimensions, duration, capture time and keywords (into `tags`, as `imported`) through one `exiftool -stay_open` process (`photo_triage.files.ExifTool`), plus Pillow for photo sizes and ffprobe for videos. After its scan, each video gets a `frames` job, which samples `VIDEO_SAMPLE_FRAMES` frames with ffmpeg into `DATA_DIR/derived/frames/<item id>/<index>.jpg` and records them in `item_frames`; photos get none, and a stage after `frames` waits for it only on videos (`media_types` on `ItemStage`). Then every item gets a `thumbnail` job, once its metadata is read and, for a video, its frames are sampled: it draws a `THUMBNAIL_SIZE` JPEG into `DATA_DIR/derived/thumbnails/large/<item id>.jpg` and a 64 px one into `…/map/`, a photo's turned by its EXIF orientation (recorded in `items.orientation`, so a 180° turn redraws them too) and a video's from its middle frame. The API serves them at `/api/items/{id}/thumbnail?size=400|64`. After its thumbnails, every item gets a `clip` job, which stores a 512-d float32 embedding in `embeddings`, tagged with the model: a photo's from the original, turned upright and, for a JPEG, decoded at reduced size (at least 448 px; the thumbnail's JPEG compression moved vectors by up to 0.06), and a video's as the mean of its frames', made unit length again. The first `clip` job loads `CLIP_MODEL` from `MODELS_DIR`; without the export there, each `clip` job fails saying where it should be, and the other stages run as usual. Everything in `DATA_DIR/derived` is regenerable, so a backup can skip it, and changing `VIDEO_SAMPLE_FRAMES`, `THUMBNAIL_SIZE` or `CLIP_MODEL` redoes the frames, thumbnails or embeddings at the next reconcile. The process starts on the first read, is started again if it dies (logged as a warning), and stops when the worker does. `just worker scan` queues a walk of `PHOTO_DIR`, which queues a scan job for each new or changed file, unless a walk is already waiting or running. It records your user name as the actor (`--actor NAME` to override), as the Activity page's "Scan now" records its viewer's. Like `noop`, it logs to stderr only. The worker also queues a walk on `SCAN_SCHEDULE` (cron, in `TZ`), checked before each claim even while paused or in quiet hours: a scheduled time is covered by any walk queued or finished since, or still unfinished, so a fresh database, or one whose worker missed several nights, gets one walk at startup. On the stack it's `just stack exec worker python -m photo_triage.worker scan`. `just worker reconcile` reconciles the item stages once and exits, as the worker does at startup; it's never a required step, since a running worker does it after every walk. A stage added, or one whose `code_version` or settings fingerprint changed, is then queued for the whole library. Before each claim it checks `worker_controls` and quiet hours, and logs at `INFO` when its state changes (`Worker paused`, `Quiet hours until …`, `Worker running; paused stages: …`). While it runs, a thread writes a heartbeat to `worker_heartbeat` every 5 s, and a clean stop records `stopped_at`, so the API can say when the worker isn't running. `just worker pause [STAGE]` and `just worker resume [STAGE]` pause and resume the whole worker, or one stage, as the Activity page does: a running worker picks the change up before its next claim, and a job already running finishes. They record your user name as the actor (`--actor NAME` to override) and log the resulting state. |
| `just image` | Lint `docker/Dockerfile` with hadolint (as pre-commit does), then build the image (`photo-triage:dev`, or `just image TAG`) with the pins from `scripts/image_pins.sh` (dev-environment §2) and run `scripts/docker_smoke.sh` on it, as the CI `docker` job does. One image runs both: the API by default (`python -m photo_triage.api --host 0.0.0.0` on port 8000, as UID 1000, with `PHOTO_DIR=/photos` and `DATA_DIR=/data`; `TRASH_DIR` keeps its default, `/photos/.photo-triage-trash`, on the library's filesystem), and the worker with the command `python -m photo_triage.worker`, after the migrate step `python -m photo_triage.db migrate`. The smoke test also runs `compose.yaml`'s migrate, app and worker services on the image. FastAPI serves the API under `/api` and the built frontend at `/`, answering any other path without a file extension (a page such as `/activity`) with its `index.html`; unknown `/api` paths and missing files are still 404s. `just api` serves `frontend/dist` too, if you've run `vite build`. |
| `just models DEST` | Copies the model weights the bootstrap put in `~/.cache/photo-triage/models` (CLIP's ONNX export, InsightFace, the aesthetic predictor) to `DEST`, the folder a Compose stack mounts as `MODELS_DIR`. It refuses if there's no CLIP export yet. |
| `just stack` | `scripts/stack.sh`: the production stack, `compose.yaml`, on an image built from the checkout (`photo-triage:dev`, as `just image` builds it, without the lint and smoke test), against the test folder `.stack/` (gitignored). The Compose project is `photo-triage-stack`, so it can't touch a real deployment. The containers run as you (`APP_UID`). `.stack/photos` is the library, with the trash inside it, and `.stack/data` is `DATA_DIR`, both bind-mounted. The containers read `.stack/app.env` in place of `.env`, created with `WORKER_NOOP_STAGE=true`; edit it to try other settings. The UI is on `APP_PORT`, from the environment or `.env`, so stop `just dev` first. Other arguments go to `docker compose` on the stack: `just stack up -d`, `just stack exec worker python -m photo_triage.worker noop 50` to queue jobs, `just stack restart worker`, `just stack logs -f`, `just stack down`. Deleting `.stack/data` starts it from an empty database. When `.stack/photos` is empty, `just stack` copies the tier-1 fixtures into it, so a scan has something to find; delete its contents to start over. See "The Compose stack" below. |
| `just map-stack [N]` | `scripts/map_stack.sh`: the production image's app alone (no worker, which would mark every item missing in the empty library), serving a synthetic library of N items (default 100,000) seeded by `scripts/seed_map.py` inside the image: clustered points, capture years, media types, 64 px thumbnails whose atlas sheets come out the size real photos' do, and the atlases. In a scratch folder, removed on Ctrl-C; the real library, `DATA_DIR` and `.stack/` are never touched, and the seed refuses a database with items. It listens on every interface on `MAP_STACK_PORT` (default 8100), for trying the map on a phone (below). `MAP_STACK_IMAGE` skips the build. Add `?fps` to the page's URL for a frame-rate readout (#119). |
| `just dry-run-full` | `compose.yaml`'s migrate, app and worker (with their caps), plus `docker/compose.dry-run.yaml`, against the whole library at `/mnt/pictures`, to measure the pipeline at scale (tier 3). It refuses to start unless `/mnt/pictures` is a read-only mount. The containers mount it read-only too, with `EXIF_WRITES_ENABLED=false`, and `DATA_DIR` and the trash in a scratch folder outside it (`~/.cache/photo-triage/dry-run`, or `DRY_RUN_DIR`). The app is on port 8010 (`DRY_RUN_PORT`). It builds the image, starts the stack detached and returns. A stopped run picks up where it left off; delete the folder to start again. `just dry-run-full report` prints the items found, the latest walk's time, each stage's items/min (busy and wall-clock), what's left and how long it would take, and the worker container's memory (`scripts/dry_run_report.py`). Other arguments go to Compose: `exec -T worker python -m photo_triage.worker scan` queues a walk, `logs -f worker`, `down`. |
| `just preview` | `scripts/scratch_stack.sh`: a throwaway copy of the app for looking at pages. It runs `scripts/dev.sh` on two free ports against empty photo, trash and data directories in a new temporary folder, with `ENV_FILE=/dev/null` so it reads no `.env`: it never sees the developer's photo library or dev database, and doesn't touch a `just dev` that's running. The noop stage is on. Once the page answers it prints `Scratch stack ready: URL` and writes `.screenshots/preview.json` (its URL and environment) for `just shot`. Ctrl-C stops it and deletes the folder and that file. |
| `just e2e` | `scripts/e2e.sh`: the end-to-end tests (§3). Builds the image, starts the Compose stack's app and worker as `photo-triage-e2e` on a free port, against a scratch copy of the tier-1 fixtures with `WORKER_FAKE_CLIP=true`, queues a scan, and runs Playwright's specs in `frontend/e2e/` at desktop and phone sizes. The stack and the scratch folder are removed afterwards, pass or fail, and on a failure the worker's last log lines are printed. Arguments go to Playwright (`just e2e --project phone`). Traces of failed tests are in `frontend/test-results/`. About 2 minutes, most of it the image build. |
| `just shot PATH` | `frontend/scripts/screenshot.ts`: full-page screenshots of `PATH` in headless Chromium, at desktop (1280×800) and phone (390×844, touch, 2× pixels) widths, saved as `NAME-desktop.png` and `NAME-phone.png` and printed. It uses a running `just preview`, or else starts a scratch stack for this shot alone (about 5 s) and stops it afterwards, so it needs nothing running. `--noop N` queues noop jobs first, `--wait SELECTOR` waits for an element, `--click SELECTOR` (repeatable) clicks first, `--viewport desktop\|phone` takes one, `--name` names the files. Scratch-stack shots go to `.screenshots/scratch/`, which `tracker.py finish` can publish (dev-environment §9). `--base URL` shoots a server that's already running, such as your `just dev`, into `.screenshots/local/`, which it won't publish, because that server can show real photos. `just shot --help` lists the options. `--wait` runs before the clicks, and both widths share one stack, so a click that changes state ("Pause all") needs `--viewport` and a run per width. Settings in the caller's environment reach the scratch stack, which stages states that are otherwise hard to reach: `TZ=UTC FAKE_NOW=2026-10-16T01:59:40+00:00 WORKER_QUIET_HOURS='Mon-Sun 02:00-07:00' just shot /activity --noop 300 --wait 'text=Quiet hours:'` runs jobs for 20 s and then shows quiet hours. To show a stopped worker, run `just preview`, freeze its worker with `kill -STOP` (find it by `DATA_DIR` in `/proc/PID/environ`, so a `just dev` worker is left alone), shoot after 30 s, then `kill -CONT` it: killing it would stop the whole stack. |
| `just db-migrate` | The migrate step: `python -m photo_triage.db migrate`, which upgrades the database in `DATA_DIR` to head, creating it if there's none. The API and worker never migrate; they check the revision at startup and exit if it isn't head, so this runs first. In the Compose stack it's the one-shot `migrate` service, which the app and worker wait for. An existing database that needs upgrading is first copied with SQLite's `VACUUM INTO` to `DATA_DIR/backups/<UTC timestamp>-from-<revision>.db`, e.g. `20261008T142305Z-from-0003.db`, and only the 5 newest backups are kept. A database newer than the code is left alone, and the step exits 1. Logs to `migrate.log`, including Alembic's lines. **Restoring a backup** is done by hand: stop the API and worker, delete `photo-triage.db-wal` and `photo-triage.db-shm` in `DATA_DIR` if they exist, copy the backup over `photo-triage.db`, and run the code whose newest migration is the revision in the backup's name. |
| `just db-reset` | Drop and re-migrate the dev database in `DATA_DIR`: Alembic downgrade to empty, then upgrade to head. For other Alembic commands, run `uv run --project backend alembic -c backend/alembic.ini …` from the repo root. A new migration starts from `revision --autogenerate`; read it before committing, since the tests fail if models and migrations disagree. |
| `just fixtures` | `scripts/make_synthetic_fixtures.py`: regenerates the tier-1 synthetic fixtures (dev-environment §4) in `backend/tests/fixtures/synthetic/`. Pillow and pillow-heif draw the photos from fixed seeds, ffmpeg makes the videos (one thread, bitexact flags, and no SIMD, whose code paths differ by CPU), and exiftool writes the metadata, so the output is byte-identical every run. That holds only for the tool versions pinned in `versions.env` and `backend/uv.lock`, so it refuses to run with any other exiftool or ffmpeg. Commit what it writes. A file in the folder that isn't part of the set is reported and left alone, and the recipe exits 1: remove it with `git rm`. `--out DIR` writes elsewhere. `tests/integration/test_synthetic_fixtures.py` regenerates the set into a temp dir and fails if any file differs from the committed one, and checks the metadata each case is meant to have, with exiftool and ffprobe. To add a case, add it to `fixtures()` in the script, run `just fixtures`, and add its check to that test. |
| `just doctor` | `scripts/bootstrap.sh --check` (tool versions, lockfile sync, backend packages with native code import, model weights, Docker, mounts read-only), then `scripts/check_env.py`: `.env` exists (or the file `ENV_FILE` names), the settings it gives are valid, `PHOTO_DIR` isn't writable when it's in `/mnt/pictures` (dev-environment §1), and a warning if the database isn't at the head revision. Exits 1 if either part fails (dev-environment §2). |

### Dev-only switches

Worker dev affordances, read from `.env` or the environment like the settings in plan §9 but not listed there:

- `WORKER_QUIET_HOURS` unset (always on). To try quiet hours, set it with `FAKE_NOW` and `TZ`: `just worker --once` then runs nothing and logs `Quiet hours until …`.
- `--once` to drain the queue and exit.
- **`FAKE_NOW`**, a controllable clock for exercising quiet hours and ETA logic. It needs a UTC offset (`FAKE_NOW=2026-10-03T21:59:00-04:00`). The worker's clock starts there and advances in real time. It sets `*_at` columns and backoff; durations in `job_stats` always come from a real monotonic timer. The API reads it too, so `GET /api/activity` shows the same quiet hours as the worker (each process starts its clock when it starts, so the two differ by the time between their starts). The worker heartbeat always uses real time.
- **`ENV_FILE`** names the file read in place of `.env`. The scratch stack sets it to `/dev/null`, so a developer's `FAKE_NOW`, quiet hours or paths can't reach it.
- **`WORKER_FAKE_CLIP=true`** makes the worker embed with `FakeClip`, which needs no model weights, under `CLIP_MODEL`'s name. `just e2e` uses it. The API's search uses it too, with a floor of 0, so about half the items match any query: enough to see search at work, though the matches mean nothing. The worker logs a warning at startup.
- **The `noop` stage**, off unless `WORKER_NOOP_STAGE=true`. `just worker noop 500` queues 500 jobs that each take 0.2 s, to watch the worker and the Activity page at work. Unlike other stages, every finished noop job is kept, so the page counts them; `just db-reset` clears them. It logs to stderr only, since a running worker owns `worker.log`.

`WORKER_THREADS` sets `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` and `NUMBA_NUM_THREADS` when the worker starts, before any ML library loads.

### The Compose stack

`compose.yaml` is the production stack (plan §3, §4; the decisions behind it are in dev-environment §5). `just stack` runs it in dev; on the server it's `docker compose up -d` in a folder holding `compose.yaml`, `docker/ollama.yaml` and a `.env`.

- **Services.** `migrate` runs the migrate step and exits; `app` and `worker` start only once it has succeeded (`service_completed_successfully`), so an upgrade is `docker compose up -d` with the new image, and the database is backed up before any migration. `app` serves the UI and API on host port `APP_PORT`, with a healthcheck on `/api/health`. `worker` gets 60 s to finish its job on a stop (`stop_grace_period`). A second worker, e.g. `docker compose run worker`, exits at once (`just worker`). `ollama` is defined in `docker/ollama.yaml`, which `compose.dev.yaml` shares, so its pinned tag is written once (dev-environment §2).
- **`.env`**, next to `compose.yaml`, is read twice. Compose takes the host side from it: `PHOTO_DIR`, `DATA_DIR` and `MODELS_DIR` are the host folders bind-mounted at `/photos`, `/data` and `/models` (read-only), and `APP_PORT` is the host port. The app containers also get it as their environment, for the rest of plan §9, with the container paths set over it. `TRASH_DIR` is always the default, `/photos/.photo-triage-trash`, so the trash is inside the library's mount and trashing is a rename (plan §6.8); there's no trash mount. `APP_ENV_FILE` names another file for the containers, as `just stack` does.
- **User.** The app, worker and migrate services run as `APP_UID`:`APP_GID` from `.env` (default `1000:1000`, the image's user), so they can be the library's owner, e.g. a NAS account, without anyone changing who owns the photos. The image works under a UID it has no name for: the worker records shell commands as `uid-N`, and numba caches in `/tmp/numba` (`NUMBA_CACHE_DIR`). If `DATA_DIR` isn't writable, each process stops at startup (exit 2) saying which UID it runs as and whose the folder is; an unwritable `PHOTO_DIR` is a warning, since trashing will fail. `scripts/docker_smoke.sh` runs the stack as UID 1234, and `just e2e` as the UID running it (1001 on CI).
- **Host folders.** `PHOTO_DIR` and `DATA_DIR` must exist and be writable by `APP_UID`. Compose doesn't create them (`create_host_path: false`), since Docker would make them owned by root. `DATA_DIR` holds the database, its backups and the logs: back that folder up. Ollama's models are in the named volume `photo-triage_ollama`.
- **Model weights** (CLIP's ONNX export, InsightFace, the aesthetic predictor) aren't in the image, which would need torch to export CLIP and grow by about 600 MB. They're in the host folder `MODELS_DIR`, mounted read-only at `/models`. The bootstrap fills `~/.cache/photo-triage/models` on the dev machine, and `just models DEST` copies it to a folder to carry to the server. `just stack` mounts the dev machine's folder (or an empty `.stack/models`), and the CI smoke test an empty one, since no stage reads the models yet.
- **Caps** (plan §6.11), so the media server's other services keep running: app 1 CPU and 1 GB, worker 4 CPUs and 6 GB, Ollama 4 CPUs and 4 GB. They're first guesses, to revisit once Phase 2 measures real work; change them in a `compose.override.yaml` on the server. To size them, copy `scripts/host_report.sh` to the server and run `bash host_report.sh [MINUTES]` there, once when it's busiest and once when it's quiet. It only reads: the CPU, memory, swap and out-of-memory kills, disks, the other containers' limits and usage, the top processes, `sar` history if sysstat is installed, and `vmstat` and `docker stats` sampled over MINUTES (default 10). It writes `~/host-report-<host>-<time>.txt`. `WORKER_THREADS` sets the worker's threads within its cap.
- **Logs.** Docker's copy of each container's stderr is capped with the `json-file` driver at 10 MB × 5 files. The app's own rotated logs are in `DATA_DIR/logs` ("Logging" below).
- **The image** is `PHOTO_TRIAGE_IMAGE`, by default `photo-triage:dev`, which `just image` builds. There's no registry yet, so on the server it's built from a checkout with `docker build $(scripts/image_pins.sh --build-arg) -f docker/Dockerfile -t photo-triage:dev .`, which needs only Docker.

### Trying the map on a phone

`just map-stack` serves a 100k-item map on port 8100 of WSL. Windows forwards `localhost:8100` to WSL by itself, so a browser on the dev machine can open `http://localhost:8100/?fps` at once. A phone on the LAN reaches WSL only through Windows, which needs a port forward to WSL's address and a firewall opening. Once the stack is up, `just map-stack` prints both commands with the address filled in; run them in a PowerShell opened with "Run as administrator". (Working the address out in PowerShell with `wsl hostname -I` isn't reliable: it runs in the default distro, which Docker Desktop can make a BusyBox one.) The firewall rule covers networks Windows calls Private; if `Get-NetConnectionProfile` says the Wi-Fi is Public, set it to Private in Windows' network settings.

The phone then opens `http://<the PC's LAN address>:8100/?fps` (`ipconfig` shows the address). WSL's address can change when it restarts, so run the portproxy line again after one. Remove both afterwards:

```powershell
netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8100
Remove-NetFirewallRule -DisplayName "photo-triage map-stack"
```

`?fps` shows, at the map's bottom right, the frames drawn in the last second and the longest gap between two of them, which is what a stutter looks like. Headless Chromium in WSL renders with SwiftShader, on the CPU, so only a real browser's numbers mean anything.

### Logging

The conventions (what each level is for, and how to get a logger) are in dev-environment §5, "Logging".

Every process calls `photo_triage.logs.configure(settings, process)` at startup, which sends one plain-text line per event to stderr and to `DATA_DIR/logs/<process>.log` (`api.log`, `worker.log`, `migrate.log`):

```
2026-10-03T22:14:05.123Z WARNING photo_triage.worker message
```

- **Timestamps are UTC with `Z`**, whatever the process's timezone, so they compare directly with the `*_at` columns. A traceback follows its line.
- **`LOG_LEVEL`** (default `INFO`; `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`, any case) sets the level for every process. Set it in `.env` or the environment and restart the process.
- **Files** rotate at 10 MB and keep 5 old ones (`api.log.1` … `api.log.5`), so a process uses at most about 60 MB. Each process has its own file, because Python's rotating handler isn't safe with several writers. With `just api` (`--reload`), only the serving child process writes `api.log`; the reloader's few lines go to stderr. In Docker, the stderr copy is capped by Compose's log options (10 MB × 5 per container).
- **Libraries** (uvicorn, SQLAlchemy, Alembic) log through the same handlers, format and level. Uvicorn's access log and SQLAlchemy's SQL statements appear only at `DEBUG`. SQLAlchemy's other loggers, such as the ORM's setup lines, are held at `WARNING`.
- **Unhandled errors in requests** are logged at `ERROR` with their traceback by `photo_triage.api.errors`, and the client gets a 500.
